
### 🔹 Практическая работа 1 пара Часть 1 (за 02.10!)
- Тема работы: Индексы (B-Tree), структуры таблиц (Heap и Clustered), селективность данных и мониторинг производительности через Query Store в MS SQL Server.
- Цель работы: Изучить физическую организацию данных, освоить оптимизацию планов выполнения запросов с помощью кластеризованных, некластеризованных и покрывающих индексов, а также провести комплексный анализ ресурсоемких процессов с помощью инструмента Query Store.


- **Что я сделал по ВСЕМ задачам:**
### Часть 1
- Задача 1: Перевел таблицу Products из состояния «кучи» (Heap) в упорядоченную структуру, создав кластеризованный индекс на базе столбца ProductID.
- Задача 2: Перевел таблицу Products из состояния «кучи» (Heap) в упорядоченную структуру, создав кластеризованный индекс на базе столбца ProductID.
- Задача 3: На примере таблицы Orders экспериментально изучил разницу в стратегиях доступа СУБД: точечный поиск одиночной строки (Index Seek), чтение диапазона (Index Seek (Range)) и полное сканирование (Clustered Index Scan) при выборке всей таблицы.
- Задача 4: Проверил влияние селективности данных на выбор плана в таблице Users. Для уникального поля Email сервер выбрал Index Seek, а для низкоселективного столбца Gender предпочел Scan, чтобы избежать медленных множественных переходов по ссылкам.
- Задача 5: Продемонстрировал изменение физического размера структуры (метрика page_count) при удалении старого и создании нового составного некластеризованного индекса по двум колонкам (Email, LastName).
- Задача 6: Оптимизировал запрос с помощью покрывающего индекса и ключевого слова INCLUDE, полностью избавив план выполнения от дорогостоящей операции Key Lookup.
- Задача 7: Проверил работу правила левого префикса на составных индексах, доказав важность порядка следования столбцов в структуре B-Tree для успешного срабатывания поиска.
- Задача 8: Сравнил производительность выполнения диапазонных запросов по датам в неструктурированной куче и упорядоченном кластеризованном индексе.


### Часть 2
- Шаг 1: Создал и развернул тестовую демонстрационную базу данных QueryStoreDemo. Перевел ее в простую модель восстановления (SET RECOVERY SIMPLE) и активировал Хранилище запросов командой ALTER DATABASE ... SET QUERY_STORE = ON. Для предотвращения зависания сессии из-за перегрузки ввода-вывода оптимизировал генератор строк с помощью конструкции SELECT TOP (50000).
- Шаг 2: Сделал принудительный сброс накопленных данных из памяти на диск через EXEC sp_query_store_flush_db. Написал и выполнил аналитический SQL-запрос к системным таблицам (sys.query_store_runtime_stats), который вывел топ-20 тяжелых запросов по времени процессора (CPU). В результатах четко выявил лидера — операцию INSERT INTO dbo.Orders, которая забрала 67213 мс процессорного времени и выполнила 580598 логических чтений, а также изучил ее текстовый план выполнения.
- Шаг 3: Открыл встроенный графический отчет «Хранилище запросов -> Топ ресурсоемких процессов» в среде SSMS. На диаграммах наглядно зафиксировал распределение общей длительности выполнения команд, где запрос с query_id = 232 (тот самый тяжелый INSERT) занял наибольшую долю, и детально изучил его плавающую точку на графике планов выполнения.
