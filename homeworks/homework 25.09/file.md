**Разница SET XACT_ABORT ON и OFF:**
1. SET XACT_ABORT ON: Если внутри транзакции происходит ошибка - автоматически прерывается выполнение скрипта, делается ROLLBACK и делается транзакцию uncommittable
2. SET XACT_ABORT OFF (по умолчанию): При некоторых ошибках SQL может пропустить ошибочную строчку кода и продолжить делать следующие команды внутри транзакции (опасно, так как может выполниться половина перевода, и баланс сломается)

- Что было сделано: Интегрировал логику перевода в защищенный блок BEGIN TRY ... END TRY. В блоке CATCH настроил автоматический откат активных транзакций через проверку @@TRANCOUNT > 0 и вывод кода/текста ошибки (деление на ноль). Описал разницу критического прерывания SET XACT_ABORT ON от стандартного режима OFF.
  
**Задание 3. Вложенные транзакции и SAVE TRANSACTION**
- Тема задания: Смоделируйте ситуацию с тремя операциями внутри одной транзакции:
1. Списание со счёта A.
2. Зачисление на счёт B.
3. Запись в лог-таблицу TransferLog.

Используйте SAVE TRANSACTION SavePoint1 после шага 1. Если шаг 3 завершается ошибкой, откатитесь только к SavePoint1 (сохранив шаги 1–2) и завершите транзакцию через COMMIT.
Вопрос для размышления в ответе: почему ROLLBACK TRANSACTION SavePoint1 не уменьшает @@TRANCOUNT?

- <img width="935" height="1072" alt="3" src="https://github.com/user-attachments/assets/39752a16-9240-46a5-af47-688a93ff2693" />


Ответ на вопросс: Потому что ROLLBACK TRANSACTION SavePoint1 не закрывает саму транзакцию, а отматывает данные назад к созданной метке как CTRL + Z. Физическая транзакция остаётся открытой, поэтому счётчик @@TRANCOUNT не меняется.

- Что было сделано:  Реализовал процесс со списанием, зачислением и логированием в TransferLog. Использовал точку сохранения SAVE TRANSACTION SavePoint1 перед логированием, что позволило успешно изолировать и откатить только сбойный шаг записи лога (передача NULL), сохранив при этом изменения балансов и успешно закоммитив их. Объяснил независимость @@TRANCOUNT от частичных откатов.

**Результаты тестирования уровней изоляции транзакций**

| Уровень изоляции | Поведение Сессии №2 (при незакоммиченной Сессии №1) | Эффект / Аномалия |
| :--- | :--- | :--- |
| **READ UNCOMMITTED** | Запрос выполняется мгновенно. Отображается измененное значение. | **Грязное чтение (Dirty Read).** Мы видим данные, которые еще не были сохранены окончательно и могут быть отменены. |
| **READ COMMITTED** | Запрос зависает в ожидании. Он ждет, пока Сессия №1 не выполнит `COMMIT` или `ROLLBACK`. | **Блокировка (Locking).** Защищает от грязного чтения. Мы видим только строго подтвержденные данные. |
| **REPEATABLE READ** | Запрос зависает в ожидании аналогично уровню READ COMMITTED. | **Блокировка (Locking).** Защищает от грязного и неповторяющегося чтения. |
| **SNAPSHOT** | Запрос выполняется **мгновенно**. Отображается старое подтвержденное значение (`10`). | **Версионирование строк (Row Versioning).** Чтение стабильного снимка данных из tempdb без каких-либо блокировок и ожидания. |

Сформировал итоговую рекомендацию для складского учета.
